# 140 人并发压测与优化报告

测试对象：数字图像处理课程竞赛平台（http://222.204.244.237:8000）
测试时间：2026-11-27
测试位置：服务器本机（127.0.0.1），排除公网带宽干扰，只测应用本身

## 一、测试环境

| 项 | 实际值 |
|---|---|
| CPU / 内存 | 128 核 / 755 GB（共享机器，压测时 load average 约 5.9） |
| 应用 | Django 5.2 + Gunicorn，SQLite（WAL） |
| 初始配置 | 3 workers × 2 threads = 6 个并发槽，timeout 90s |
| 压测工具 | requests + 140 线程 + Barrier 同时起跑（真并发尖峰） |
| 数据 | 140 个专用压测账号（B0001–B0140），走完整登录/上传/评分链路 |

## 二、第一轮：3 个 worker 的原始配置

### 并发登录 140 人（每人 1 次 GET + 1 次 POST）

| 指标 | 结果 |
|---|---|
| 总耗时 | **193.9 秒** |
| 吞吐 | 1.4 req/s |
| p50 | 3 243 ms |
| p95 | **189 472 ms** |
| 最大 | 191 711 ms |
| 失败 | 20 个请求超时（共 280 个） |

同时观察到 Gunicorn 在压测期间重启了全部 3 个 worker（日志 `Booting worker`），说明 worker 被超时杀死后重建，请求在客户端侧挂死近 3 分钟。

**这个配置撑不住 140 人同时登录。**

### 瓶颈定位

三层原因叠加，不是一个问题：

1. **会话写库争抢 SQLite 单写锁**。默认 `SESSION_ENGINE` 是数据库会话，每个请求都要写 `django_session` 表；登录还要再写一次 `last_login`。SQLite 在 WAL 模式下仍然只有一个写者，140 个并发登录就是在一条队列上排队等写锁，等锁期间连接被占住，形成雪崩。
2. **并发槽只有 6 个**。140 人 ÷ 6 ≈ 24 轮排队。机器有 128 核，配置严重偏小。
3. **密码哈希是纯 CPU 操作**。PBKDF2 单次 0.31 秒（实测），140 次就是 43 秒纯计算，GIL 下每进程约只有 1 个线程能真正推进哈希。

## 三、优化措施

| 改动 | 位置 | 原因 |
|---|---|---|
| 会话改为签名 Cookie（`signed_cookies`） | `web/settings.py` | 彻底消掉每请求的 session 表写入，登录只剩一次 `last_login` 更新，写锁争用消失 |
| workers 3 → 10，threads 2 → 4，timeout 90 → 120 | `deploy/dip-competition.service` | 用上 128 核，并发槽 6 → 40 |
| 输入图改用 640px JPEG 缩略图 | `competition/views/base.py` | 原始输入图 1.3 / 1.5 MB，见下节 |
| 输入图缓存 300 秒 → 1 天 | 同上 | 赛程内图片不变，学生反复刷新不该重复下载 |
| 图片卡固定高度、显式宽高 | `app.css` / `task.html` | 消除图片加载引起的布局跳动（CLS） |

## 五、结论

**在 140 人同时使用的场景下，当前配置可以正常支撑。** 三类主要操作全部零失败：

- 同时登录：最慢 3.1 秒，95% 在 2.6 秒内
- 同时浏览：95% 在 1.2 秒内
- 同时上传评分：最慢 7.1 秒，95% 在 6.3 秒内（含完整 PSNR/SSIM 计算）

六年级前的配置（3 worker + 数据库会话）在 140 并发登录时会直接崩溃，这是本次压测发现的最严重问题，现已修复。

## 六、仍可优化（按性价比排序）

1. **上传评分 6.3 秒偏长**。瓶颈是同步计算 PSNR/SSIM + 1.3 MB 文件落盘。若要压到 3 秒以内：把 workers 提到 20（128 核完全够），或改成"先返回、后台算分"的异步评测（需要引入任务队列，复杂度高）。在课堂场景下 6 秒可接受——学生上传后本来就需要看到分数。
2. **没有反向代理**。Gunicorn 直接监听 8000 端口对外，静态文件靠 WhiteNoise 在 Python 进程里发。建议加 Nginx 托管 `/static/` 并做 gzip，能让首页再快 30–50%，同时获得连接复用和慢客户端保护。
3. **SQLite 写并发上限**。上传峰值时 140 个并发写仍会排队。当前规模没问题；若以后扩到几百人同时提交，或需要多人同时改成绩，应切 PostgreSQL（配置里已预留 `DB_ENGINE=postgres`）。
4. **首轮冷启动的偶发慢请求**。第一轮压测中 `/submissions/` 出现过一次 26.8 秒的极值，出现在 worker 刚重启、Python 模块尚未预热时。可通过给 worker 加 `--preload` 或压测前先手动访问一次来避免。
5. **密码哈希可换 Argon2**。PBKDF2 每次 0.31 秒是登录的主要 CPU 开销。换成 Argon2id 可降到约 0.05 秒且更安全，但已下发的学生密码仍是 PBKDF2 哈希（首次登录才自动升级），所以只对新导入的班级有明显收益。
